# Отчёт по проекту: автоматический подбор музыки для коротких видео

## 1. Постановка задачи

Цель проекта — реализовать прототип системы, которая по короткому видео подбирает наиболее подходящую музыкальную дорожку из набора кандидатов. Задача сформулирована как retrieval: для видео и аудио строятся векторные представления в общем пространстве, после чего музыка ранжируется по близости к видео.

Такой подход отличается от задачи классификации: модель не выбирает один заранее заданный класс, а сравнивает видео с набором музыкальных кандидатов. Поэтому для оценки используются retrieval-метрики: Hit@1, Hit@5 и MRR.

## 2. Данные

В качестве источника данных выбран датасет HarmonySet (`Zzitang/HarmonySet`). Он содержит пары видео и музыки, YouTube-ссылки на ролики и текстовые аннотации. Датасет удобен для учебного проекта, потому что уже содержит пары "видео - музыка", но при этом сами видео нужно скачивать отдельно.

Пайплайн подготовки данных состоит из нескольких шагов:

1. Скачивание метаданных HarmonySet с Hugging Face.
2. Скачивание доступных YouTube-видео через `yt-dlp`.
3. Проверка видео через OpenCV.
4. Создание `manifest.csv` только с валидными роликами.
5. Разбиение данных на train, validation и test.

Так как часть YouTube-ссылок недоступна или скачивается некорректно, фактический размер датасета меньше запрошенного лимита. В одном из экспериментов при запуске на подвыборке около 500 исходных примеров было обработано 421 видео из manifest, из них 418 успешно получили видео- и аудиопризнаки. Три ролика были пропущены из-за ошибок чтения кадров.

Сейчас дополнительно запущен более крупный эксперимент с лимитом около 1500 исходных примеров. Его результаты будут добавлены после завершения извлечения признаков и обучения.

## 3. Извлечение признаков

Для ускорения обучения признаки извлекаются заранее и сохраняются в `.npy` файлы. Это позволяет не прогонять видео и аудио через feature extractors на каждой эпохе.

### 3.1 Видео

Из каждого видео равномерно выбирается несколько кадров. В текущей версии используется `frame_count = 16`. Каждый кадр пропускается через предобученный ResNet50 из `torchvision`. Последний классификационный слой ResNet50 заменяется на `Identity`, поэтому сеть возвращает не вероятности классов ImageNet, а 2048-мерный вектор признаков.

Для одного видео признаки по всем выбранным кадрам усредняются. В результате каждое видео представляется одним 2048-мерным вектором.

Изначально использовался ResNet18, который возвращал 512-мерный вектор. Позже backbone был заменён на ResNet50, потому что он даёт более богатые визуальные признаки и потенциально должен улучшать качество retrieval.

### 3.2 Аудио

Аудиодорожка извлекается из видео через `ffmpeg` в mono wav. Далее используется `librosa`: считается mel-спектрограмма, затем она переводится в log-mel шкалу через `power_to_db`.

Для каждой mel-полосы считаются два значения: среднее и стандартное отклонение по времени. В текущей версии используется `n_mels = 96`, поэтому аудиовектор имеет размерность `2 * 96 = 192`.

Такой способ простой и быстрый. Он не является полноценным музыкальным энкодером, но позволяет получить компактное описание тембра, энергии и частотного распределения аудио.

## 4. Модель

Используется two-tower архитектура:

- video tower принимает визуальный вектор;
- audio tower принимает аудиовектор;
- обе башни переводят признаки в общее embedding space;
- затем эмбеддинги нормализуются через L2-нормализацию.

В текущей конфигурации размерность общего эмбеддинга равна 256. В обеих башнях используется структура:

1. Linear(input_dim, 256)
2. ReLU
3. Dropout(0.15)
4. Linear(256, 256)
5. L2-нормализация

Dropout был добавлен после первых экспериментов как простая регуляризация, потому что данных сравнительно немного, а модель может переобучаться.

## 5. Обучение

Модель обучается contrastive loss. В одном batch находятся правильные пары "video - audio". Для каждого видео правильным считается аудио с тем же индексом в batch, а остальные аудио в batch выступают отрицательными примерами.

Считается матрица сходства между всеми видео- и аудиоэмбеддингами в batch. Далее используется cross-entropy loss в двух направлениях:

- video -> audio;
- audio -> video.

Итоговый loss — среднее между двумя направлениями. Такой вариант делает обучение более симметричным и стабильным.

Текущие параметры обучения:

- `batch_size = 48`
- `epochs = 30`
- `learning_rate = 0.0005`
- `weight_decay = 0.0001`
- `temperature = 0.07`
- `embedding_dim = 256`

### 5.1 Ход экспериментов

Работа велась постепенно. Сначала был собран более лёгкий baseline, чтобы проверить, что весь пайплайн запускается от скачивания данных до оценки модели. В первой версии использовалась подвыборка около 300 исходных примеров, ResNet18 для видео, 64 mel-полосы для аудио, меньший batch size и embedding dimension 128. Сначала обучение запускалось на 15 эпохах. Такой запуск был быстрым и помог проверить корректность подготовки данных, извлечения признаков и расчёта метрик.

После этого число эпох было увеличено до 30, чтобы проверить, продолжает ли снижаться training loss и улучшаются ли retrieval-метрики. По результатам стало видно, что loss действительно снижается, но метрики на validation/test остаются шумными из-за небольшого количества примеров и простых признаков.

Далее конфигурация была усилена: ResNet18 заменён на ResNet50, число кадров увеличено до 16, число mel-полос до 96, размер общего эмбеддинга до 256, batch size до 48. Эта версия стала заметно тяжелее по времени, особенно на этапе извлечения признаков, но должна давать более информативные представления видео и аудио.

## 6. Метрики

Для оценки используются:

- Hit@1 — доля запросов, где правильная аудиодорожка стоит на первом месте.
- Hit@5 — доля запросов, где правильная аудиодорожка попала в топ-5.
- MRR — среднее значение обратного ранга правильного ответа.

Также считается random baseline. Это важно, потому что абсолютные значения метрик зависят от размера test split. Например, если в test split 63 кандидата, случайный Hit@1 равен примерно `1 / 63 = 0.0159`.

## 7. Текущий эксперимент: ResNet50, около 500 исходных примеров

На текущем доступном эксперименте после фильтрации и извлечения признаков получилось 418 объектов. Test split содержал 63 кандидата.

По логам обучения loss постепенно снижался: примерно с 3.6 в начале до 2.67 к 30-й эпохе. При этом validation MRR оставался шумным и невысоким, что ожидаемо для небольшой выборки.

Результаты на test split:

| Метод | Hit@1 | Hit@5 | MRR | Mean rank | Число кандидатов |
| --- | ---: | ---: | ---: | ---: | ---: |
| Model | 0.0159 | 0.1429 | 0.0905 | 30.90 | 63 |
| Random baseline | 0.0159 | 0.0794 | 0.0751 | - | 63 |

По этим значениям видно, что модель пока не улучшает Hit@1 относительно случайного выбора, но заметно улучшает Hit@5: 0.1429 против 0.0794. MRR также немного выше random baseline: 0.0905 против 0.0751.

Это означает, что модель часто не ставит правильную музыку на первое место, но чаще, чем случайный baseline, поднимает её в верхнюю часть ранжирования. Для небольшого учебного baseline это можно считать рабочим результатом, но качество пока нельзя назвать высоким.

## 8. Эксперимент: около 1500 исходных примеров

После эксперимента на меньшей подвыборке был запущен более крупный прогон с лимитом около 1500 исходных примеров. Извлечение признаков с ResNet50 оказалось самым долгим этапом: скачивание видео заняло около 40 минут, а извлечение признаков — примерно 2 часа. Это связано с тем, что для каждого видео нужно прочитать несколько кадров, прогнать их через ResNet50, а также извлечь и обработать аудиодорожку.

На большем запуске test split содержал 187 кандидатов. Это делает задачу заметно сложнее: при большем числе аудиокандидатов вероятность случайно поставить правильную дорожку высоко в ранжировании уменьшается. Поэтому метрики нельзя напрямую сравнивать только по абсолютному значению без учёта размера пула кандидатов.

По логам обучения loss снизился примерно с 3.8 до 1.03 к 30-й эпохе. Это показывает, что модель хорошо подстраивается под train split. При этом validation MRR оставался низким и менялся слабо: в последние эпохи он находился примерно в диапазоне 0.04-0.06. Это говорит о том, что модель учится на обучающих парах, но обобщение на новые пары остаётся слабым.

Результаты на test split:

| Метод | Hit@1 | Hit@5 | MRR | Mean rank | Число кандидатов |
| --- | ---: | ---: | ---: | ---: | ---: |
| Model | 0.0107 | 0.0321 | 0.0394 | 84.01 | 187 |
| Random baseline | 0.0053 | 0.0267 | 0.0311 | - | 187 |

Модель снова оказалась лучше random baseline по всем трём метрикам: Hit@1 примерно в два раза выше случайного выбора, Hit@5 также выше baseline, MRR выше на небольшую величину. При этом абсолютные значения стали ниже, чем в эксперименте на 500 исходных примерах. Это ожидаемо, потому что в test split теперь 187 кандидатов вместо 63, и найти правильную музыку среди большего числа вариантов сложнее.

Главный вывод по большому эксперименту: увеличение данных помогло сделать проверку более честной и сложной, но сама архитектура всё ещё остаётся слабым baseline. Простые log-mel статистики и усреднение кадров через ResNet50 не дают достаточно сильного мультимодального представления, чтобы уверенно ставить правильную музыку на первое место.

### 8.1 Попытка усложнить башни (и откат к более простой модели)

После эксперимента на подвыборке около 1500 исходных примеров была сделана попытка улучшить качество за счёт усложнения two-tower башен: добавлены дополнительные полносвязные слои, `LayerNorm`, `GELU` и более сильный `Dropout`, скрытый размер 512. Признаки не пересчитывались, обучение запускалось на тех же `.npy` файлах.

По логам обучения `train_loss` оставался высоким и снижался медленно: примерно с 3.39 на 26-й эпохе до 3.16 на 30-й. При этом `val_mrr` на графике динамики обучения почти не отличался от нуля и не показывал стабильного роста. Это признак того, что модель плохо использует валидационный сигнал при текущих признаках и размере данных.

Результаты на том же test split из 187 кандидатов:

| Метод | Hit@1 | Hit@5 | MRR | Mean rank |
| --- | ---: | ---: | ---: | ---: |
| Model (глубокие башни) | 0.0107 | 0.0321 | 0.0390 | 91.60 |
| Random baseline | 0.0053 | 0.0267 | 0.0311 | - |

Для сравнения, на тех же данных с более простыми башнями (два `Linear`, `ReLU`, `Dropout(0.15)` без `LayerNorm`) получалось:

| Метод | Hit@1 | Hit@5 | MRR | Mean rank |
| --- | ---: | ---: | ---: | ---: |
| Model (простые башни) | 0.0107 | 0.0321 | 0.0394 | 84.01 |

Hit@1 и Hit@5 совпали до четырёх знаков, но у глубоких башен MRR оказался немного ниже (0.0390 против 0.0394), а средний ранг правильной дорожки хуже (91.60 против 84.01). В совокупности с плохой динамикой на validation это совпадает с ощущением, что более сложная архитектура в данном setup не дала выигрыша и ухудшила ранжирование.

Поэтому в коде проекта было принято решение вернуться к более простой архитектуре башен. Дальнейшие улучшения разумнее искать в признаках и данных, а не в чрезмерном увеличении глубины MLP на текущем уровне сигнала.

## 9. Ограничения проекта

Главные ограничения текущего решения:

1. Данные зависят от доступности YouTube-ссылок. Часть видео не скачивается или не читается.
2. Видео представляется средним вектором по кадрам. Такая схема почти не учитывает динамику и временную синхронизацию.
3. Аудио представляется простыми log-mel статистиками. Это слабее, чем использовать специализированный аудиоэнкодер вроде CLAP.
4. Положительная пара берётся как исходное видео и его аудио. Это соответствует структуре HarmonySet, но не всегда означает, что музыка субъективно лучшая для видео.
5. Размер выборки пока ограничен временем скачивания и извлечения признаков в Colab.

## 10. Возможные улучшения

Дальше качество можно улучшать в нескольких направлениях:

- увеличить размер выборки и использовать результаты текущего запуска на 1500 исходных примерах;
- заменить аудиопризнаки на CLAP или другой предобученный музыкальный энкодер;
- использовать CLIP/ViT для видеофреймов вместо ResNet50;
- добавить временную модель поверх последовательности кадров, а не просто усреднять их;
- добавить hard negative mining;
- провести ручную оценку нескольких top-k рекомендаций.

## 11. Вывод

В проекте реализован полный retrieval pipeline для задачи подбора музыки к видео: загрузка данных, фильтрация видео, извлечение видео- и аудиопризнаков, обучение two-tower модели, оценка через retrieval-метрики и сравнение с random baseline.

Текущий эксперимент показывает, что даже простая модель начинает ранжировать правильные пары лучше случайного выбора по Hit@5 и MRR, но качество остаётся ограниченным. Основные причины — небольшой объём данных, простые аудиопризнаки и отсутствие явного моделирования временной структуры видео и музыки.

Эксперимент на большей подвыборке подтвердил, что модель обучается и показывает результат выше random baseline, но качество остаётся ограниченным. Дополнительная попытка усложнить башни не дала улучшения на тех же признаках, поэтому в проекте оставлена более простая архитектура.
